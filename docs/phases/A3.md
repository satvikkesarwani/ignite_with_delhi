## The latency budget — read this before designing anything

`backend/aiService.js:49`: _"Nemotron emits a visible thinking phase; simple prompts take
25s+"_. A four-call agent loop is 100 seconds of dead air in front of a judge.

**Hard budget: at most ONE LLM call per user question.** Everything else is a Cypher
template or deterministic string building. Design to this constraint, do not treat it as a
nice-to-have — it is the difference between a demo that feels sharp and one that feels
broken.

## Build 1 — `backend/resolveService.js` (the existence check)

_"including existence checks"_ is named in the judging criteria. The dataset plants the trap
deliberately: **two different people are both named Shiv Sharma**, plus a `Shivam Sharma`, a
`Shiv Verma`, and `Aarav Malhotra` who does not exist at all.

`resolve(nameOrEmail)` — a ladder, stopping at the first tier that yields results. Zero LLM
calls:

1. Exact email match
2. Exact normalized name (lowercase, collapse whitespace, strip punctuation)
3. Neo4j full-text `person_search` index (built in A1)
4. Trigram / Levenshtein fuzzy, threshold 0.75, for typos

Return:

```js
{ status: 'found',      match: {...} }                      // exactly 1 confident hit
{ status: 'ambiguous',  matches: [...], question: "..." }   // 2+ hits — ASK, never guess
{ status: 'not_found',  suggestions: [...] }                // nearest names, honestly labelled
```

The `question` must disambiguate on a _distinguishing_ attribute, not a generic prompt:
`"I found two people named Shiv Sharma — one at IIT Delhi (ML/AI, 7 hackathons) and one at
Amity Noida (Backend, 2 hackathons). Which one?"`

For `not_found`, say so plainly and offer the nearest names. **Never invent a person.** A
confident hallucination here loses the round; an honest "not in the database" wins it.

## Build 2 — `backend/retrievalService.js` (template-first routing)

Classify the query, then route. Classification is **regex + keyword matching, not an LLM**.

**Tier 1 — Cypher templates (0 LLM calls, <100ms).** Hand-write parameterized Cypher for
the intents an organizer actually has. Cover at least:

- person lookup by name → delegates to `resolveService`
- filter by college / skill / grad year / city
- filter by persona or status (`dormant`, `rising`, `active`)
- "top N by X" (wins, engagement, mentor score, submission rate)
- "who won <track/hackathon>"
- "who has not attended since <date>"
- "who can we email" (consent + no recent outreach)
- repeat teammates of a person

Parse entities out with regex against **vocabularies read from the graph** (college names,
skill names, hackathon names, track names). A user saying "DTU" or "Delhi Technological
University" must hit the same template.

**Tier 2 — text2cypher fallback (1 LLM call), only when no template matches.** Guardrails,
all mandatory:

- Inject the full schema (labels, properties, relationships) into the prompt
- Few-shot with 4 template examples
- **Reject** any generated Cypher matching
  `/\b(CREATE|MERGE|DELETE|DETACH|SET|REMOVE|DROP|CALL\s+apoc\.(?!coll))\b/i`
- Force `LIMIT 50` if absent
- Run with a 10s timeout; on error or empty, fall to Tier 3

**Tier 3 — honest failure.** _"I could not turn that into a reliable query. Here is what I
can answer…"_ with 3 example questions. Never fabricate.

Return `{rows, strategy: 'template:top_n' | 'text2cypher' | 'fallback', cypher, latency_ms}`.
**Surface `strategy` and `cypher` in the API response** — showing the generated Cypher on
screen is a strong credibility move with technical judges.

## Build 3 — `backend/agentService.js`

`POST /api/agent/chat` — `{message, sessionId}`.

Flow:

1. Detect intent: _is this about one named person_, or _a segment search_?
2. Person → `resolveService`. If `ambiguous`, **return the question immediately, zero LLM
   calls, sub-second.** This is the single best moment in the demo — make it instant.
3. If resolved → load that stored `ContextProfile`. The narrative is already written, so
   for "tell me about X" you can answer with **zero** LLM calls. Only call the LLM when the
   question is narrower than the narrative ("how active has he been?", "would he mentor?"),
   passing the profile JSON as the sole context.
4. Segment → `retrievalService`, return rows plus a deterministic one-line rationale per
   row built from graph facts (`"3 hackathons, 1 win, Python from 14 repos"`). **Do not
   generate 20 rationales with an LLM.**
5. Always return `citations[]`: `{claim, source_type, source_ref}` drawn from the profile's
   `evidence[]`.

System prompt: `/no_think`, answer only from supplied context, never state a number not in
the context, say "I don't have that" when the context is silent.

Session memory: in-memory `Map` keyed by `sessionId`, last 6 turns, so _"and what has he
built?"_ resolves against the previously discussed person. Do not persist it.
