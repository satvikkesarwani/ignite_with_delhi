## The one rule

**The LLM never computes a number.** Every count, rate, date and ranking comes from Cypher.
The LLM receives computed values and writes prose about them. If you let Nemotron count
hackathons it will confidently say 3 when the answer is 7, and the agent-quality score dies
with it. This rule is not negotiable anywhere in this file.

## Stage 1 — Signals (pure Cypher, zero LLM)

One query per user returning the `facts` block from `docs/CONTRACT.md`:
registered / attended / no-shows, projects submitted, submission rate, wins with rank and
track, best rank, average and median score, first seen, last active, days since active,
mentor session count and average score, interaction count by type, workshops, distinct
teammates and repeat teammates, outreach sent/opened/clicked/replied, consent flag.

Write it as **one Cypher query with `OPTIONAL MATCH` per signal**, not eight round-trips per
user. 600 users × 8 queries on Aura free tier is minutes of latency you do not have.

Read the signal list from `config/domain.hackathon.json` so it stays config-driven — that is
the generalizability story and it costs almost nothing to do now.

## Stage 2 — Skills with confidence and provenance

Merge three sources into one ranked list. Do not just union them.

| Source                                     | Weight | Evidence string                     |
| ------------------------------------------ | ------ | ----------------------------------- |
| Declared on signup                         | 0.3    | `"self-declared at signup"`         |
| GitHub language %                          | 0.9    | `"68% of 22 public repos"`          |
| Used in a submitted project                | 0.8    | `"built P0031 with it, scored 88"`  |
| Mentioned in judge feedback / mentor notes | 0.6    | `"judge noted strong PyTorch work"` |

`confidence = 1 - Π(1 - weight_i)` across sources, capped at 0.97. Never output 1.0.

**Then detect the gap.** If a skill is declared but has no evidence source, flag
`claim_gap: true` with `"declared, but no supporting repo or project"`. Conversely flag
`hidden_strength: true` for a skill with strong evidence that was never declared. User
`U0015` (declares ML, GitHub is 90% JavaScript) exists in the dataset specifically to
demonstrate this — verify it fires on him.

This one feature will separate you from every other team. It is the clearest possible proof
that you built a context layer and not a join.

## Stage 3 — Traits, personas, trajectory (deterministic rules)

Traits, each `{trait, score 0-1, evidence[]}` — rules from the domain config:

`serial_finisher` (submission rate), `starter_not_finisher`, `no_show_risk`,
`team_player` (repeat teammates), `lone_wolf`, `mentor_material` (mentor score + answered
questions), `specialist` vs `generalist` (skill entropy across tracks),
`competitive_performer` (wins per attendance), `community_active` (interaction volume).

Personas are named combinations for the UI — max 2 per user, chosen by highest score:
`Serial Winner`, `Rising Star`, `Dormant High-Potential`, `Mentor Material`,
`Consistent Builder`, `Ghost`, `Newcomer`.

Trajectory — this is the "behaves over time" requirement, do not skimp:

- `score_series[]` in chronological order, and `direction` from a linear fit:
  `rising | steady | declining | insufficient_data`
- `status`: `active` (<60d), `cooling` (60–180d), `dormant` (180–365d), `lapsed` (>365d)
- `tech_drift`: skills in their two most recent projects that appear in none of their
  earliest two — rendered as `"React → LangChain, Neo4j"`
- `engagement{value, components{recency, frequency, depth, outcome}}` — each component
  0–100, and **store the components**, never just the total. When a judge asks "why 78?"
  you open the breakdown. A bare score looks made up.

Verify against the story users: `U0009` Kabir must come out `rising`, `U0008` Rohan must
come out `dormant` with wins, `U0010` Meera must be `starter_not_finisher`.

## Stage 4 — Narrative (the only LLM call, and it is offline)

4–6 sentences: who they are, what they are good at _with evidence_, how they have behaved
over time, and one line of organizer-relevant judgement.

- Prompt template lives in `config/domain.hackathon.json` under `narrative_prompt`
- Pass **only computed values** in a compact JSON block. Never raw rows.
- System prompt must include: `/no_think`, _"use only the supplied values"_, _"state no
  number that is not in the input"_, _"if a field is null, omit it — never guess"_
- `temperature: 0.4`, `maxTokens: 400`
- Use the existing `generateChat` from `backend/aiService.js`. It rotates 5 keys
  automatically, but each call takes ~25s — so:

**Batching for 600 users:** run with concurrency 5 (matching the key pool), a progress
counter, and checkpointing to `data/profiles/<user_id>.json` after each one so a crash
resumes instead of restarting. 600 × 25s ÷ 5 ≈ 50 minutes wall time — start this running in
the background and continue working while it goes.

**Do not block the demo on it.** Order the queue: story users `U0001`–`U0017` first, then
users with the most activity, then the rest. Anyone without a narrative yet gets a
deterministic template string — the UI must never show an empty profile.
