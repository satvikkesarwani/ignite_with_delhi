## Part A — Cognee semantic layer (batch only)

**The constraint:** `cognifyService.js:24` says a real cognify takes 2–5 minutes. So it runs
**once, offline, over the text corpus** — and never on a request path.

### Build the corpus

The unstructured text in the dataset is what Cognee is actually for. Nothing else:
project descriptions, judge feedback, mentor notes, interaction text.

`scripts/build_cognee_corpus.js` → one document per person:

```
PERSON U0001 Shiv Sharma — IIT Delhi
PROJECT "LegalRAG" (GenAI track, 2025-04): <description>
JUDGE FEEDBACK (rank 1, score 92): <feedback>
MENTOR NOTE (2025-04, rated 5): <notes>
INTERACTION (2025-04-11): <text>
```

Prefix every line with the `user_id` so retrieved chunks are traceable back to a person.
Write to `data/cognee_corpus/*.txt`.

### Run it

`scripts/cognify_corpus.js` posts to `POST /api/cognify/run` in batches. **Start with the 17
story users only** — that is ~4 minutes and covers everything the demo touches. Run the
remaining 583 in the background afterwards only if there is time and budget.

Point the Cognee service at the same AuraDB (`GRAPH_DATABASE_URL` in
`services/cognee-service/.env`) so its semantic entities live in the same graph as the
structured nodes. That shared-graph story is the strong technical answer to *"how are
Cognee and Neo4j actually working together?"* — and note that `neo4jService.js:127` already
filters out Cognee's `DocumentChunk` / `TextSummary` bookkeeping nodes from the
visualization, so the graph view stays clean.

### Use it — one narrow, honest job

Add a **Tier 1.5** to `backend/retrievalService.js`, between templates and text2cypher:
when the query is conceptual rather than structural (*"creative builders"*, *"good with
decentralized tech"*, *"people who think about accessibility"*), call
`cognifyService.searchMemory()`, map the returned chunks back to `user_id`s, then **expand
those seeds through Neo4j** to apply hard filters and pull full profiles.

That is the genuine hybrid: semantic recall, graph precision. Keep it to that one job.

**Feature-flag it** (`ENABLE_COGNEE_RETRIEVAL`) and make it fall through to text2cypher on
any error or timeout. It must never be able to break a demo query.

## Part B — Eval harness

`data/eval_questions.json` has 25 questions with ground truth computed from the data.

`scripts/run_eval.js` — fire each at `POST /api/agent/chat`, compare, score by type:

- `count` / `existence` / `not_found` — exact match
- `ambiguity` — did it ask instead of guessing? (binary, and this is the one to highlight)
- `ranking` — is the top result correct?
- `trend` / `consent` — does the answer contain the required assertion?

Output a table: question, expected, got, PASS/FAIL, latency, strategy. Then overall accuracy
and mean latency, written to `docs/EVAL.md`.

**Then actually fix the failures** — the harness is a tool, not a deliverable. Expect the
misses to cluster in text2cypher; each fix is usually one more Cypher template, which also
makes that query faster. Re-run until you are above 85%.

Put the final number on a slide. *"24 of 25, mean 1.2 seconds"* is concrete in a way that no
amount of architecture description is, and almost no other team will have it.

## Part C — Hardening (do not skip)

1. **Cache every external call.** Tavily and GitHub responses to `backend/cache/`, committed.
   Add `OFFLINE_MODE=1` that serves only from cache. Venue wifi fails; assume it will.
2. **Snapshot the profiles.** Confirm `data/profiles/*.json` is current and committed, and
   that the disk fallback from C1 actually works with Neo4j stopped. **Test it by stopping
   Neo4j**, not by reading the code.
3. **Seed the demo path.** A script that pre-warms story-user profiles, pre-runs the demo
   queries, and pre-generates the outreach paragraphs into cache. First-query latency in
   front of a judge should be zero.
4. **Fix `docs/ISSUES.md`**, highest severity first.
5. **Deploy and verify.** Push; confirm Render and Vercel are green; set every env var in
   the Render dashboard (they are not read from `.env` there); load the live URL on a phone
   hotspot to prove it works off your laptop.
6. **Record a 3-minute fallback video** of the full demo. If the network dies during
   judging, you play it and keep talking. This has saved more hackathon teams than any
   feature.
7. **Write `docs/DEMO.md`** properly: the beat-by-beat script from `C1.md` extended with
   intake, outreach and matchmaking, with the exact sentence for each beat and who drives.
   Include the use-case justification — *"we chose a hackathon platform; external context
   (GitHub, public web) is relevant here because the platform's value is technical
   capability, which is why a food-delivery config would switch it off"* — because
   `Use-case clarity` is the first criterion on the sheet and it is won with one clear
   sentence.
