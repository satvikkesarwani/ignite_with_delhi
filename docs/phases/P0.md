## Build these, in order

### 1. `docs/CONTRACT.md` — the single source of truth

Write out, in full:

**a) The graph schema.** Nodes and their properties:
`Person, Hackathon, Team, Project, Result, Skill, College, Company, Mentor, MentorSession,
Interaction, OutreachEvent, ContextProfile, RawEvent`
Relationships:
`REGISTERED_FOR, ATTENDED, MEMBER_OF, BUILT, ACHIEVED, HAS_SKILL, STUDIED_AT, WORKED_AT,
MENTORED_BY, PERFORMED, RECEIVED, TEAMMATE_OF, ABOUT, DERIVED_FROM`
Every relationship carries `{source, observed_at}` so provenance survives traversal.

**b) The `ContextProfile` JSON schema**, exactly as specced in `docs/PLAN.md` §5. Expand
each field with types and one example value. This object is the contract between the
backend and the frontend — the frontend renders it, the agent cites it.

**c) The REST API.** Request and response shape for each:

```
GET  /api/crm/stats                      -> counters for the header strip
GET  /api/crm/candidates                 -> ?q=&college=&skill=&persona=&status=&sort=&limit=&offset=
                                            { rows[], total, facets{} }
GET  /api/crm/candidates/:userId         -> full ContextProfile
GET  /api/crm/candidates/:userId/graph   -> { nodes[], links[] } evidence subgraph
POST /api/crm/resolve                    -> { name } -> { status: found|ambiguous|not_found,
                                            matches[], question? }
POST /api/crm/segment                    -> { query } -> { rows[], strategy, cypher,
                                            rationale_by_user_id{}, latency_ms }
POST /api/agent/chat                     -> { message, sessionId } -> { answer, citations[],
                                            table[], strategy, cypher, latency_ms }
POST /api/crm/intake                     -> multipart -> { userId, profile, stages[] }
POST /api/crm/outreach                   -> { userIds[], template, subject?, body? }
                                            -> { sent[], previewUrls[] }
POST /api/crm/match                      -> { userId?, requirements? } -> { matches[] }
```

**d) Error envelope.** Every endpoint returns `{ success, error, requestId }` on failure.
Note that `server.js` already stamps `X-Request-Id` — reuse it, do not invent a new one.

**e) The hard rule**, stated prominently: *the LLM never computes a number. All counts,
rates, dates and rankings come from Cypher. The LLM only narrates values handed to it.*

**Aesthetic direction — commit to this, it is deliberately not the default dark-glass look:**

An *editorial intelligence terminal*. Warm near-black paper, ochre as the single accent,
dense and data-first, generous horizontal rhythm but tight vertical rhythm.

```css
--bg:        #12100E   /* warm near-black, NOT slate/zinc */
--surface:   #1A1815
--border:    #2A2723
--text:      #EDE8E0
--muted:     #9A9186
--accent:    #C8892A   /* ochre */
--positive:  #6E8B6B   /* sage */
--warning:   #C4873F
--danger:    #B4553F   /* clay */
```

- Type: **Fraunces** (headings, 600) + **IBM Plex Sans** (body) + **IBM Plex Mono** (all IDs,
  counts, dates, scores). The serif/mono contrast is what stops it reading as AI-generic.
- Layout: fixed **left rail** nav (icon + label, 220px), content area asymmetric —
  never a centered hero, never a centered anything.
- Cards: 4px radius, 1px border, **no drop shadows**, no `rounded-2xl`. Separate with
  borders and space, not elevation.
- Tables are the primary surface: 32px rows, mono for numeric columns, right-aligned
  numbers, sticky header, hairline row borders.
- Zero gradients. Especially no purple→blue.

Put these as CSS custom properties on `:root` in `frontend/src/index.css` and map them into
`tailwind.config.js` under `theme.extend.colors`. Also define them under
`@media (prefers-color-scheme: light)` — but dark is the default and the demo mode.

Build exactly **three** shadcn primitives now so B1 is not blocked: `button`, `input`,
`badge`. Nothing else.
