The CSV gave us 600 historical users. This phase adds the **live** path: a new participant
submits a form and a resume, and seconds later they are a fully contextualized person in the

*continuous* rather than a one-off batch job.

## Read this first — the timing constraint that kills the naive design

`backend/cognifyService.js:24`: `PIPELINE_TIMEOUT_MS = 480000` — *"real cognify takes 2-5
min"*. `backend/aiService.js:49` — Nemotron is ~25s per call.

**Cognee cannot be on the request path.** If you await `runEclPipeline` inside
`POST /api/crm/intake`, the demo hangs for minutes in front of a judge.

Correct design:

```
POST /api/crm/intake   (synchronous, target < 40s total)
  stage 1  parse PDF            pdf-parse        ~1s
  stage 2  structure it         1 Nemotron call  ~25s
  stage 3  external enrich      Tavily + GitHub  ~3s   (parallel with stage 2)
  stage 4  write graph          deterministic    ~1s
  stage 5  build profile        reuses A2        ~2s   (narrative reuses the stage-2 call)
  -> returns the complete profile

  then, fire-and-forget: enqueue cognify. Poll GET /api/crm/intake/:jobId/status.
```

Stages 2 and 3 run concurrently with `Promise.all` — that is the difference between 28s and
53s, and it is the whole perceived quality of the demo.

## Build

### 1. `backend/resumeParser.js`

`npm i multer pdf-parse` (both missing). Extract text, then **one** Nemotron call returning
strict JSON: `{education[], experience[], skills[], projects[], links[]}`.

- `/no_think`, `temperature: 0.2`, explicit JSON schema in the prompt
- Nemotron will sometimes wrap JSON in prose or fences — strip fences, extract the
  outermost `{...}`, `JSON.parse` in a try/catch, and on failure fall back to a regex
  skill-keyword scan against the skill vocabulary already in the graph. **Never 500 because
  the model returned prose.**
- Cap input at 8000 chars. Reject non-PDF and files over 10MB at the multer layer.

### 2. `backend/tavilyService.js` — new file

- `searchPerson({name, college, githubUsername})` → Tavily search, top 5 results, extract
  title/url/snippet
- `fetchGitHub(username)` → the public GitHub API directly (no token needed for 60 req/hr):
  repo count, top languages by bytes, followers, recent push dates, top 5 repos. This is
  more reliable and far richer than scraping, so prefer it whenever a username exists.
- **Cache everything** to `backend/cache/tavily/<hash>.json` and `cache/github/<user>.json`,
  and commit the cache. On the demo machine you must never depend on the venue wifi or a
  rate limit.
- 6s timeout, and on any failure return `{available:false, reason}` — never throw. A missing
  external source degrades the profile, it does not fail the request.
- **Do not scrape LinkedIn.** It breaches their terms and will burn 40 minutes on a block
  page. Use Tavily for public pages, and be upfront in the pitch that LinkedIn-shaped data
  is synthetic. Judges respect a stated boundary; they do not respect a broken scraper.

### 3. `backend/intakeService.js`

Orchestrates the five stages. Then:

- **Dedupe:** `MERGE (p:Person {email})`. If they exist, enrich rather than duplicate, and
  return `{isReturning: true}` so the UI can say *"welcome back — profile updated"*. That
  detail sells the "context accumulates over time" story better than any slide.
- Write `(:RawEvent {source:'form'|'resume'|'tavily'|'github', observed_at})` for every
  extracted claim, so a live-added person has the same evidence trail as a CSV one. Make
  sure the drawer's evidence panel is populated for them — a judge will check.
- Reuse `contextBuilder.js` unchanged. Same code path as the CSV. **Say this out loud in the
  demo** — it is the architecture answer.
- Return `stages[]` with real per-stage `{name, status, ms, detail}` for the UI stepper.

### 4. Endpoints

`POST /api/crm/intake` (multipart), `GET /api/crm/intake/:jobId/status`.

### 5. Prepare the demo asset

Put a real resume PDF in `demo/sample_resume.pdf` — use a teammate's, or generate one. Run
it through the pipeline now and fix whatever breaks. **Do not first run this at the demo.**

## Acceptance

- `curl -F` with the sample PDF returns a full `ContextProfile` in **under 40s**
- Submitting the same email twice enriches, does not duplicate — verify node count
- With Tavily and GitHub both unreachable, intake still succeeds with a degraded profile
- A corrupt/garbage PDF returns a clean 400, not a stack trace
- The new person appears in `/api/crm/candidates` and is findable by `/api/crm/resolve`
- Their evidence trail is populated and visible in the drawer
- The cognify job is enqueued and its status endpoint reports honestly

## Do not

- Do not await cognify in the request
- Do not make more than 2 LLM calls per intake
- Do not scrape LinkedIn
- Do not fork `contextBuilder.js` — reuse it, that is the whole point
